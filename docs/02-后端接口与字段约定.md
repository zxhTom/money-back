# 后端接口与字段约定（配合小程序身份证密文化）

本文档供**后端**实现与联调时对照；字段名可按贵司规范微调，但需在 Swagger/接口文档中保持**与小程序设计文档一致**。

## 1. 总体原则

1. **密文**：用户与合同中的证件号字段使用**同一套加密/编码**，保证小程序可用 `===` 做当事人与当前用户是否一致的判断（在双方都使用密文字段的前提下）。
2. **展示字段**：单独下发，格式固定为 **前 6 位 + 中间全部为 `*` + 后 4 位**（长度与星号数量由后端统一，小程序不做拼接）。
3. **明文**：小程序**不依赖**接口下发明文身份证；确需明文时由小程序调用**解密接口**按需获取。

## 2. 用户信息类接口

### 2.1 获取用户资料（如 `GET /system/user/profile/get`）

建议在响应 `data` 中明确：


| 字段            | 类型     | 必填  | 说明                         |
| ------------- | ------ | --- | -------------------------- |
| `idNo`        | string | 是   | **证件号密文**（业务主值，与合同侧一致）     |
| `idNoDisplay` | string | 是   | **仅展示**：前 6 + 中间 `*` + 后 4 |
| ~~明文证件~~      | —      | 否   | **不应再返回**                  |


若历史兼容需要暂时保留明文字段，请标注废弃时间，并与前端约定优先级。

### 2.2 更新用户资料（如 `PUT /system/user/profile/update`）

- 用户**修改证件**：请求体传 **明文** 或贵司规定的「前端加密后再传」二选一，需文档说明。
- 用户**未修改证件**：请求体**不传** `idNo` 或传**与 GET 一致的密文**（二选一，需固定一种避免误覆盖）。

## 3. 合同类接口

### 3.1 合同详情 / 列表项中的当事人

对每个「证件号」建议成对返回，例如：


| 字段                  | 说明          |
| ------------------- | ----------- |
| `indebtedId`        | 借款人证件**密文** |
| `indebtedIdDisplay` | 借款人展示串      |
| `creditorId`        | 出借人证件**密文** |
| `creditorIdDisplay` | 出借人展示串      |


协议模板、富文本中若内嵌证件号，建议后端直接拼好 **Display** 或占位符，避免小程序从密文推导。

### 3.2 创建 / 更新合同

- 小程序可能传当事人**密文**（从用户资料带出）或**明文**（用户手输）；请后端统一校验与入库策略，并返回密文 + Display。

## 4. 解密接口（按需）

### 4.1 用途

- 人脸识别、实人认证、极少数必须明文的外联系统；**禁止**用于普通列表展示。

### 4.2 建议形态（路径仅为示例）

`POST /custom/contract/dashboard/id-card/decrypt`  
或统一放在 admin-api 下贵司已有规范路径。

### 4.3 请求


| 字段                      | 类型     | 说明                               |
| ----------------------- | ------ | -------------------------------- |
| `cipher` / `idNoCipher` | string | 与 profile/合同中一致的密文               |
| `scene`                 | string | 可选：枚举如 `face_auth`、`export`，便于审计 |


### 4.4 响应


| 字段               | 说明             |
| ---------------- | -------------- |
| `plain` / `idNo` | 明文身份证（仅在此接口返回） |


### 4.5 安全要求（请后端必须落地）

- 必须 **登录态**（`Authorization`）。
- **频率限制** + **审计日志**（谁、何时、何场景、解了哪类业务对象）。
- 可选：同一用户每日解密次数上限。
- 错误码区分：无权限、参数非法、解密失败。

## 5. 分享与深链

若分享路径中携带「发起人标识」：

- **方案 A**：携带**证件密文**（需评估 URL 长度与编码；密文需 URL-safe）。
- **方案 B（推荐）**：携带 `**userId` 或 `shareToken`**，由服务端解析，**不在 URL 中出现证件**。

请后端与小程序约定 `**contract-share-entry` 页**的 query 参数最终方案，并同步更新小程序构建分享路径的代码。

## 6. 人脸 / H5 回调

- 若 H5 必须带明文：建议改为后端生成 **一次性 `token`**，小程序只传 token；或 H5 内由后端会话换明文。
- 若仍必须小程序传明文：在调用解密接口后拼接，且 **URL 长度与日志脱敏** 需评估。

## 7. 联调检查清单

- profile 仅返回密文 + `idNoDisplay`，无长期明文字段。
- 合同详情当事人密文与 profile 密文可 `===` 匹配（同一用户同一证件）。
- 解密接口返回明文且仅此时出现明文。
- 更新资料不会用 Display 误覆盖密文。
- 分享链接打开合同逻辑在「密文 / userId / token」方案下闭环。
