Money Web 认证显示与 TDK 用户列表问题定位
日期：2026-11-11，时间均为北京时间

一、实际根因及证据

1. 数据库已认证，但 Web 显示未认证
数据库及用户本人 /system/user/profile/get 返回 verified=1。
管理端 /system/user/page、/system/user/get 使用 UserRespVO，该响应对象没有 verified 字段。
Web 使用 row.verified === 1 判断状态；缺字段时按未认证处理，修改弹窗又将 expectedVerified 设成 0。
这是接口响应缺字段与前端默认值共同造成的问题，不是用户本人认证数据未保存。

2. 修改时出现错误提示
当天日志中的两次 /system/user/update-verified 请求：
16:45:38、16:46:08，均返回业务码 400，消息为“认证状态已变化，请刷新列表后重试”。
请求带 expectedVerified=0、verified=1，而数据库实际已是 1，后端并发校验正确拒绝了请求。
线上前端源码及发布产物原本就调用 message.success；现有证据不能把这两次失败说成成功被误标为错误。
正确修复需要补齐真实状态，只有服务端确认成功时才显示成功提示，不能把 400 强行涂绿。

3. contractmanager 在 TDK 查询用户列表 403
修复前，相同有效账号和查询条件：正式后端及 ORG 返回 code=0，TDK 返回 HTTP 403 HTML。
TDK 的 Nginx location /admin-api/system/user/page 直接 return 403，绕过了后端角色权限判断。
2026-11-10 部署备份 tdk.conf 中已经存在这条无条件拦截。

三、为什么测试没有发现

原人工认证前端测试给模拟数据注入 expectedVerified=0，只检查提交载荷、刷新与异常后按钮恢复。
它没有从真实后端转换对象生成 JSON，没有断言列表、详情、本人接口的认证字段一致。
TDK 的部署测试只证明切换时限制仍存在，没有从有权限账号的使用路径验证需求。
之前只核对数据库就判断“无需处理”，也遗漏了 Web 响应与显示链路。
这些是实现、联调及验收覆盖不足，不能用“测试通过”代替实际功能可用。
