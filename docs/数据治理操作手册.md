# 数据治理操作手册

## 概述

本系统存在两类随时间积累的数据：

| 类别 | 说明 | 本文操作 |
|------|------|--------|
| **日志数据** | API 访问、登录、短信、支付通知等，每次请求或操作自动写入，无需长期保留 | ✅ **立即可操作** |
| **历史业务数据** | 已完结合同、已支付订单等，有业务价值但访问频率极低 | 📋 **备用方案，需要时再操作** |

---

## 场景一：清理日志数据（立即可操作）

### 原理

代码层面已全部实现。每个日志表对应一个定时 Job，按设定的保留天数，每天凌晨将过期日志**物理删除**（分批删除，每次 100 条，不影响数据库性能）。

**你只需要在管理后台注册这些 Job，它们就会自动运行。**

---

### 操作步骤

#### 第一步：登录管理后台

访问系统管理后台 → 顶部菜单选择「**基础设施**」→ 左侧菜单选择「**定时任务**」。

#### 第二步：参照已有任务格式

页面上已有以下 3 个任务在运行，可以参照它们的格式：

| 任务名称 | Handler 名称 |
|--------|------------|
| 访问日志清理 | `accessLogCleanJob` |
| 错误日志清理 | `errorLogCleanJob` |
| 定时任务日志清理 | `jobLogCleanJob` |

点击任意一条查看详情，你会看到如下字段：
- **任务名称**：任意描述性文字
- **Handler 名称**：必须与代码中的 Bean 名称完全一致
- **CRON 表达式**：执行时间规则
- **参数**：可留空
- **状态**：开启

#### 第三步：逐一新增以下 12 个任务

点击「**新增**」按钮，按下表填写，每条任务单独新增一次：

| 任务名称（可自定义） | Handler 名称（必须完全一致） | 保留天数 | 建议 CRON |
|-----------------|--------------------------|---------|----------|
| 登录日志清理 | `loginLogCleanJob` | 30 天 | `0 0 2 * * ?` |
| 操作日志清理 | `operateLogCleanJob` | 90 天 | `0 10 2 * * ?` |
| 短信日志清理 | `smsLogCleanJob` | 30 天 | `0 20 2 * * ?` |
| 邮件日志清理 | `mailLogCleanJob` | 30 天 | `0 30 2 * * ?` |
| 数据访问日志清理 | `dataAccessLogCleanJob` | 30 天 | `0 40 2 * * ?` |
| 审计日志清理 | `auditLogCleanJob` | 90 天 | `0 50 2 * * ?` |
| 安全告警清理 | `securityAlertCleanJob` | 180 天 | `0 0 3 * * ?` |
| 支付通知日志清理 | `payNotifyLogCleanJob` | 30 天 | `0 10 3 * * ?` |
| 商品浏览记录清理 | `productBrowseHistoryCleanJob` | 30 天 | `0 20 3 * * ?` |
| 订单日志清理 | `tradeOrderLogCleanJob` | 90 天 | `0 30 3 * * ?` |
| 售后日志清理 | `afterSaleLogCleanJob` | 90 天 | `0 40 3 * * ?` |
| 签到记录清理 | `signInRecordCleanJob` | 365 天 | `0 50 3 * * ?` |

> **CRON 说明**：`0 0 2 * * ?` 表示每天凌晨 2:00 执行。上表中将 12 个任务的执行时间错开 10 分钟，避免同时运行。

#### 第四步：验证运行结果

任务新增后，可以立即手动触发验证：
1. 找到刚新增的任务，点击「**执行一次**」
2. 执行完成后，点击「**日志**」查看结果
3. 日志中应显示类似：`定时执行清理登录日志数量 XXX 个`

若显示 `0 个` 是正常的，说明当前没有超过保留期的数据。

---

### 各日志表保留期说明

| 日志表 | 保留期 | 选择原因 |
|-------|--------|---------|
| 登录日志（system_login_log） | 30 天 | 安全审计基本需求 |
| 操作日志（system_operate_log） | 90 天 | 业务操作追溯需要 3 个月 |
| 短信日志（system_sms_log） | 30 天 | 短期排查即可 |
| 邮件日志（system_mail_log） | 30 天 | 短期排查即可 |
| 数据访问监控（custom_data_access_log） | 30 天 | 安全监控滚动窗口 |
| 审计日志（custom_audit_log） | 90 天 | 合规审计需要 |
| 安全告警（custom_security_alert） | 180 天 | 安全事件需要较长回溯 |
| 支付通知日志（pay_notify_log） | 30 天 | 仅用于排查通知失败 |
| 商品浏览记录（product_browse_history） | 30 天 | 推荐算法短期数据 |
| 订单日志（trade_order_log） | 90 天 | 订单纠纷追溯 |
| 售后日志（trade_after_sale_log） | 90 天 | 售后纠纷追溯 |
| 签到记录（member_sign_in_record） | 365 天 | 签到奖励发放依赖历史 |

> 如需调整保留天数，修改对应 Job 类中的 `JOB_CLEAN_RETAIN_DAY` 常量后重新部署即可。

## 场景二：历史业务数据归档（备用，需要时操作）

> **当前不需要操作**。当主库数据量导致查询变慢，或磁盘空间紧张时，再按本节操作。

### 原理

将主库中 **1 年以上已完结的业务数据**（合同、支付订单等）迁移到独立的归档数据库，主库只保留近期活跃数据。需要查看历史数据时，系统自动从归档库读取。

---

### 前置条件

需要准备一台独立的归档数据库服务器（或在同一 MySQL 实例上创建新 Schema），规格可以比主库低。

---

### 操作步骤

#### 第一步：创建归档数据库

在数据库服务器上执行以下脚本（需将 `contract` 替换为实际的主库库名）：

```bash
mysql -h <数据库地址> -u root -p < money-back/sql/mysql/archive/01_create_archive_database.sql
```

该脚本会创建 `contract_archive` 数据库，并建立所有归档表（结构与主库一致，额外多一个 `archive_time` 字段）。

#### 第二步：修改配置文件

编辑 `yudao-server/src/main/resources/application-prod.yaml`，将 `archive` 数据源指向真实的归档数据库地址：

```yaml
# 找到以下配置段并修改
datasource:
  dynamic:
    datasource:
      archive:
        lazy: true
        url: jdbc:mysql://<归档数据库地址>:3306/contract_archive?useSSL=false&...
        username: <用户名>
        password: <密码>
```

修改后重新部署服务。

#### 第三步：在管理后台注册归档任务

进入「**基础设施 → 定时任务**」，新增以下任务：

| 任务名称 | Handler 名称 | 说明 | 建议 CRON |
|--------|------------|------|----------|
| 合同历史归档 | `contractArchiveJob` | 归档 12 个月前已完结/取消的合同 | `0 0 4 1 * ?`（每月1日凌晨4点）|
| 支付订单历史归档 | `payOrderArchiveJob` | 归档 12 个月前已完结的支付订单 | `0 30 4 1 * ?`（每月1日凌晨4:30）|

> 归档任务建议设置为**每月**执行一次，选择业务低峰期（凌晨 4 点后）。

#### 第四步：验证归档结果

1. 手动触发任务「执行一次」
2. 查看任务日志，应显示：`合同归档完成，共归档 XXX 条`
3. 登录归档数据库，查询 `contract_archive.custom_contract` 表确认数据已写入
4. 查询主库 `custom_contract` 表，确认对应记录已删除

---

### 查询历史数据

归档后，通过系统正常查询合同详情时，代码会自动做回退查询（主库没有 → 去归档库查），**用户无感知**。

如果需要将某条历史记录从归档库**恢复到主库**（例如需要修改历史合同），可以调用以下接口（需开发对应 Controller，或直接执行 SQL）：

```sql
-- 1. 查看归档库中的记录
SELECT * FROM contract_archive.custom_contract WHERE id = <合同ID>;

-- 2. 手动将该记录插回主库
INSERT INTO contract.custom_contract
SELECT id, ... FROM contract_archive.custom_contract WHERE id = <合同ID>;

-- 3. 从归档库删除（可选）
DELETE FROM contract_archive.custom_contract WHERE id = <合同ID>;
```

### 扩展更多表的归档

目前已实现示例：合同（`custom_contract`）、支付订单（`pay_order`）。

其他需要归档的表按相同模式操作，开发工作量约每张表 2~3 小时：

| 表名 | 建议归档条件 |
|-----|------------|
| pay_refund | 已退款 + 1 年前 |
| pay_wallet_transaction | 1 年前 |
| trade_order | 已完成 + 1 年前 |
| member_point_record | 2 年前 |
| trade_brokerage_record | 已结算 + 2 年前（注意财务合规保留要求）|
| ai_chat_message | 90 天前 |

> ⚠️ **财务类数据注意**：`pay_wallet_transaction`、`trade_brokerage_record` 等涉及财务流水的表，在归档前请确认是否有监管合规要求（一般为 5~7 年）。建议这类表只归档，不从归档库删除。
